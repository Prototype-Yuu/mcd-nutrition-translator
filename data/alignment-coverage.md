# 数据对齐覆盖率

> 实测数据（2026-10-24，门店 `1450713` 麦当劳上海黄浦华旭国际大厦餐厅）。
> 复现：`python3 scripts/normalize.py --nutrition data/nutrition-snapshot.json --menu data/menu-snapshot.json --aliases data/aliases.json --out data/alignment-report.json`

## 数字

| 项 | 值 |
| --- | --- |
| 营养表条目 | 160 |
| 单店菜单条目 | 129 |
| **精确命中** | 25 |
| **去规格命中** | 7 |
| **别名命中** | 5 |
| 命中合计 | **37（28.7%）** |
| 歧义 | 0 |
| 未命中 | 92 |

未命中按原因：

| 原因 | 数量 | 说明 |
| --- | --- | --- |
| `combo`（套餐/多件套） | 45 | 三件套、四件套、双人餐、分享餐、随心选——营养表只按单品给数据，没有套餐聚合值 |
| `no_tier`（无对应单品） | 47 | 季节限定（龙焰系列）、周边玩具（按摩捶/贴纸）、部分饮品小食 |

## 为什么命中率是 28.7%，而不是更高

**因为官方营养表和门店菜单没有共同的键**：

- `list-nutrition-foods` 按**餐品名称**返回营养，`nutritionDescription` 全 null，无餐品编码
- `query-meals` 按**餐品编码**返回菜单，名称在 `data.meals` 字典里

要把两者对上，只能靠名称。而两边的命名体系并不一致：菜单有 45 个套餐/多件套组合，营养表却只有单品。

## 一个重要的设计取舍：关闭相似匹配

第一版对齐曾启用字符相似度匹配（Dice bigram）和包含匹配，把命中率推到 31.8%。但抽查发现——**这两个层级在真实数据上 100% 误配**：

```
'培根蔬萃双层牛堡三件套' -> '培根蔬萃双层牛堡'   (fuzzy)
'麦辣鸡翅4块套餐'        -> '麦辣鸡翅-2块'      (containment)
```

套餐的热量是**各组成部分之和**，远高于单品。把套餐配成单品，会系统性地低估热量——这是比"查不到"更危险的错误。

所以默认**关闭**了相似匹配和包含匹配，宁可命中率低、不误配。当前 37 个命中全部来自精确 / 去规格 / 别名三层，零误配。

## 未命中怎么处理（不补救、如实说）

- **套餐**：不在营养表里。要算套餐，正确做法是 `query-meal-detail` 拆出 `rounds[].choices[]` 再逐项求和——这是迭代期路线，见 Roadmap。
- **季节限定 / 周边**：营养表本来就没有，判"未收录"，不插值。
- **杯型**（可乐/雪碧/薯条等通称）：菜单用通称，营养表按中杯/大杯/小杯分，本项目用别名默认取中杯（见 `data/aliases.json`），属项目约定。

## 失败样例（人工可查）

完整逐条记录在 `data/alignment-report.json`，每个餐品带 `method` 和 `score`。挑几个典型的：

| 菜单名 | 结果 | 层级 |
| --- | --- | --- |
| 巨无霸 | ✅ 巨无霸 | exact |
| 麦辣鸡腿汉堡三件套 | ❌ 套餐 | combo |
| 龙焰芝士棒鸡腿堡三件套 | ❌ 套餐 | combo |
| 阳光橙麦炫酷 | ❌ 无对应 | no_tier |
| 可乐 | ✅ 可乐中杯 | alias（默认中杯） |

## 这意味着什么

这个 28.7% 不是缺陷，是**事实**：麦当劳官方接口目前无法用营养数据覆盖套餐。任何声称"能算套餐热量"的同类项目，要么用相似匹配在猜，要么根本没对齐。

本项目选择把这件事摊开——匹配算法、覆盖率报告、失败样例全部开源，可复现、可审计。
