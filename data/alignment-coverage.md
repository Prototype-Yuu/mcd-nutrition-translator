# 数据对齐覆盖率

> 状态：**待真实数据填充**。
> 本文件在取得 MCP Token 并跑通 `list-nutrition-foods` 与 `query-meals` 后生成，数字会来自真实调用，不是估算。

## 为什么这件事值得单独一份报告

官方的营养数据和门店菜单**没有共同的键**：

- `list-nutrition-foods` 按**餐品名称**返回营养数据，不返回餐品编码
- `query-meals` 按**餐品编码**返回菜单，不返回餐品名称

要算出一单的合计营养，只能在中间加一层名称对齐。而两边命名并不一致（菜单带规格后缀、营养表带份量说明），所以对齐命中率直接决定了这个 Skill 能覆盖多少真实点餐场景。

## 将要记录的内容

| 项 | 说明 |
| --- | --- |
| 营养表条目数 | `list-nutrition-foods` 返回的行数 |
| 单店菜单条目数 | 某个 `storeCode` 下 `query-meals` 返回的行数 |
| 精确命中 | 归一化后完全一致 |
| 去规格命中 | 去掉"中/大/单点"等后缀后一致 |
| 别名命中 | 命中维护的别名表 |
| 歧义 | 一个名称对上多个营养行，不自动取值 |
| 未命中 | 营养表里没有这个餐品 |
| 命中率 | 精确 + 去规格 + 别名 / 菜单总数 |

## 复现方式

```bash
python3 scripts/normalize.py \
  --nutrition data/nutrition-snapshot.json \
  --menu data/menu-snapshot.json \
  --out data/alignment-report.json
```

输出的 `by_method` 就是上面那张表的分子，`results` 里逐条保留了每个餐品的命中层级与分数，可以人工抽查。

## 已知的失败形态

按设计会出现的三种情况，都不做补救：

1. **名称带季节限定后缀**（"龙焰芝士棒鸡腿堡三件套"）——营养表通常没有对应行，判 `unmatched`
2. **通用词对上具体产品**（"鸡腿堡" vs "麦辣鸡腿堡"）——匹配器要求候选项至少 4 个字符且长度差 ≤ 2，避免吞并
3. **同名不同规格**（"香芋派" 与 "香芋派（大）"）——判 `ambiguous`，不自动取值
